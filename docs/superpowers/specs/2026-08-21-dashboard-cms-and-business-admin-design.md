# Dashboard CMS + Partner Business Admin — Design Spec

Expands the Kobly staff dashboard (`apps/dashboard`) into a lightweight,
WordPress-style admin: page-content management (Part 1) and partner-business
(flyttebyrå) management (Part 2), on top of the existing Django project. This
document is the repo owner's original brief, plus the two decisions it
explicitly delegated ("pick one and justify") and the investigation needed to
unblock Part 2's "leads received" view.

## Resolved: which lead pipeline is live

Investigated before writing the plan, since Part 2 §2 depends on the answer:

- `apps.leads.MoveLead` (the wizard at `/flytteforesporsel/`) is the only
  lead-submission path reachable from any current template. It saves the
  lead and emails a receipt; it never touches `Bedrift_info` or
  `JobDistribution`.
- `core.Flytteforesporsel` + `store.JobDistribution`, fed by
  `send_flytteforesporsel` (`apps/core/views.py:73`), is still routed live
  at `POST /send-flytteforesporsel/` (`demo/urls.py:34`) and fully
  functional — but a repo-wide search of every template
  (`apps/**/templates/**/*.html`) for `send_flytteforesporsel` /
  `send-flytteforesporsel` returns zero matches. Nothing in the current
  site calls it. It is reachable only by hitting the URL directly (e.g.
  curl/Postman), not through any user-facing flow.
- Consequence: `JobDistribution` currently holds zero rows generated by
  real traffic in this port, and the business's own self-service "received
  leads" view (`apps.userprofile.views.foresporsel_database`, which also
  queries `JobDistribution`) is equally empty today for the same reason.

Per the brief's instruction, Part 2's "leads received" list still queries
`JobDistribution` (the only model that actually links a lead to a
business) — that's the correct long-term integration point, and it's also
what the business's own account page already reads, so staff and the
business see the same data source. The business-detail template must carry
a code comment stating plainly that this list will be empty until
`send_flytteforesporsel` (or a successor) is wired into a live template,
so nobody mistakes an empty table for a bug.

## Resolved: `apps/pages` is a new app, not an extension of `apps/dashboard`

`apps/dashboard` is reused for both parts' *admin UI* (views, urls,
templates, the `staff_required` decorator) — that matches the brief's
"reuse the dashboard shell" instruction for Part 2, and there's no reason
to duplicate it for Part 1.

The `Page`/`PageSection` *models* go in a new `apps.pages` app instead of
living inside `apps.dashboard`, because the rendering integration in Part 1
requires `apps/core/views.py` (home, about, for_business, ...) to import
these models directly — and `apps.core` must not depend on `apps.dashboard`
(an internal admin tool depending on nothing but the models it edits; a
public-facing rendering app depending on an admin app would be the
dependency pointing the wrong way, and would make `apps.core` drag in
`apps.dashboard`'s admin-only views/urls just to read a `Page` row). Giving
the content model its own app keeps `apps.core` (reads `Page`) and
`apps.dashboard` (reads/writes `Page`) as two independent consumers of one
shared, front-end-agnostic model app — the same relationship
`apps.dashboard` already has with `apps.leads.MoveLead`.

`apps.pages` needs adding to `INSTALLED_APPS` in `demo/settings.py`
(gitignored — the edit takes effect live but won't show in `git diff`).

## PART 1 — Page content management
======================================================================

### Goal

Turn the dashboard into a page manager staff can use the way they'd use
wp-admin's "Pages" screen: see every page on the site in one list, open one
to edit its text and images, duplicate a page to use as a starting point
for a new one, and control whether a page is live.

### Scope decision (already made by the brief)

Full generic block-builder (drag-and-drop, arbitrary new block types) is
NOT the target for v1 — these templates have a fixed, known set of
sections per page (hero, image strip, stats, services, testimonials, FAQ,
how-it-works, trust, CTA, footer — see `home.html`). Build "section-level"
editing: each existing template section becomes an editable block with
typed fields (heading, subline, body text, button label/href, image), not
a freeform rich-text canvas.

### Data model — `apps/pages/models.py`

- `Page`: `title`, `slug` (unique), `path` (real URL, e.g. `/om-oss/`),
  `template_key` (identifies which Django template/view this maps to —
  `"home"`, `"about"`, `"for_business"`, ...), `status`
  (`draft`/`published`), `created_at`, `updated_at`, `updated_by` (FK
  `User`, nullable — set from `request.user` on save).
- `PageSection`: FK `Page` (`related_name="sections"`), `order`
  (`PositiveIntegerField`, default ordering), `section_type` (`hero`,
  `image_strip`, `stats`, `services`, `testimonials`, `faq`,
  `how_it_works`, `trust`, `cta`, `footer`, `generic_text`), typed fields
  (`heading`, `subheading`, `body_text`, `button_label`, `button_href`,
  `image` `ImageField`), plus an `extra_json` `JSONField` (default
  `dict`) escape hatch for list-like content (FAQ Q&A pairs, testimonial
  quotes, service cards, step cards) instead of a table per type.
- Images upload to `MEDIA_ROOT/pages/` via `ImageField(upload_to="pages/")`
  — same `MEDIA_URL`/`MEDIA_ROOT` already used for `business_images/` and
  `business_logos/` (`demo/settings.py:135-136`).

### Rendering integration — must be backward compatible

- Each `apps/core/views.py` view (`home`, `about`, `for_business`,
  `for_business_partner`, `contact`) looks up
  `Page.objects.filter(template_key=..., status="published").first()` and
  passes it, plus its sections keyed by `section_type` (or ordered list),
  into the template context as `page`.
- Templates prefer `page` section data when present, falling back to the
  current hardcoded copy/image when `page` is `None` or a section is
  missing — e.g.
  `{{ section.heading|default:"Vi finner det beste flyttebyrået for deg" }}`.
- `home.html` is migrated first as the reference implementation (richest
  section set — hero, image_strip+stats, how_it_works, testimonials,
  trust, services, cities, faq, footer_cta, per the current template at
  `apps/core/templates/core/home.html:6-266`). Every other page stays on
  its hardcoded fallback until explicitly migrated in a later pass. A page
  with no `Page` row must render exactly as it does today — zero `Page`
  rows in the DB is the default/tested state, not an edge case.

### Dashboard admin UI (extends `apps/dashboard`, reuses `staff_required`)

1. **Pages list** (`dashboard:page_list`, nav link in `_base.html` topbar
   next to Leads): title, path, status badge, last updated + by whom,
   actions Edit / Duplicate / View live / Delete. Mirror the existing
   `lead-table` markup/JS (clickable row → edit).
2. **Page editor** (`dashboard:page_edit`): page-level fields (title,
   path, status) + one form block per `PageSection`, showing only the
   fields relevant to its `section_type`. Image fields show the current
   image plus a replace input. POST-and-redirect, same style as
   `update_status`/`delete_lead` (`apps/dashboard/views.py:74-88`).
3. **Duplicate** (`dashboard:page_duplicate`, POST-only): clones `Page` +
   all its `PageSection`s (copying image files byte-for-byte via Django's
   storage API — `ContentFile(src.read())` saved under a fresh name, not
   just re-pointing the new row at the same file) into a new `Page` with
   `status="draft"`, title suffixed `" (kopi)"`, a unique slug/path
   (`-kopi`, `-kopi-2`, ... suffix if taken). Redirects to the new page's
   editor.
4. **New page**: the only creation path in v1 is "duplicate an existing
   page" — every page needs a `template_key` to render somewhere, and
   there's no page-from-scratch flow.
5. Norwegian UI copy throughout, matching existing dashboard vocabulary
   ("Slett", "Lagre", "Publiser", "Utkast").

### Non-goals

No generic block builder, no new page templates from scratch, no WYSIWYG
library. Don't touch `apps/leads`, `apps/store`, `apps/userprofile`
templates in Part 1. Don't change `MoveLead` dashboard behavior/URLs.

### Acceptance criteria

- Migrations run cleanly; existing pages render unchanged with zero `Page`
  rows in the DB.
- Home page gets `PageSection` rows seeded via a management command from
  its current hardcoded copy; editing a section in the dashboard changes
  what renders live.
- Staff can view list, edit+save text/image, duplicate, publish/unpublish,
  delete — no Django admin needed. Delete/duplicate require POST + CSRF.

## PART 2 — Partner business (flyttebyrå) management
======================================================================

### Context specific to this part

Businesses already have a full data model in `apps/store/models.py` — no
new models needed here, this is "build a staff-facing admin UI over
existing models," reusing the dashboard shell:

- `Bedrift_info`: company/contact fields, `cities` (comma-separated
  string), `move_type` (comma-separated string), `leads_per_day`/
  `leads_per_week`/`leads_per_month` (`CharField`s, parsed with
  `int(x or 0)` at match time in `send_flytteforesporsel` — cast
  carefully, keep as strings in forms), `total_leads_received`
  (`CharField`, incremented as a string→int→string round trip in
  `apps/core/views.py:163-167` — preserve that behavior exactly, don't
  "fix" the type without checking that call site), `priority_score`
  (`CharField`, 1–10, defined on the model but never read anywhere in the
  matching logic in `send_flytteforesporsel` — flag as dead/unused in the
  editor, don't imply it does anything), `active` (`BooleanField`,
  default `False` — currently toggleable only via Django's stock
  `/admin/`, nowhere in the custom dashboard or the business's own account
  pages).
- `PublicBusinessInformation` (OneToOne with `Bedrift_info`): `logo`,
  `about_us`, `faq` (freeform text, "line breaks separate
  questions/answers" per its `help_text`).
- `BusinessImage`: up to 6 per business (enforced in `.clean()` —
  `apps/store/models.py:78-80`), gallery images.
- `Review`: `rating` (1–5) + `comment` + `name`, FK to `Bedrift_info`. No
  public submission endpoint anywhere in the codebase (confirmed: not
  referenced in `apps/core`, `apps/leads`, or `apps/userprofile` views) —
  reviews are staff/admin-entered testimonials today, not
  customer-submitted. Keep that model: staff create/edit/delete reviews
  for a business from the dashboard.
- `JobDistribution`: FK to `core.Flytteforesporsel` + `business_1/2/3` —
  see the pipeline resolution above.
- Businesses already self-serve some of this from a *separate* logged-in
  business account area (`apps/userprofile/views.py` `edit_public_profile`,
  `foresporsel_database` — templates under
  `apps/userprofile/templates/core/accountPages/`). Part 2 builds the
  STAFF view of the same data (plus fields the business can't touch
  themselves: `active`, `priority_score`, which cities/move_types they're
  matched on) — a parallel read/write surface over the same models, not a
  replacement for the business's own account pages. Don't modify
  `apps/userprofile` in this part.

### Dashboard admin UI

1. **Businesses list** (`dashboard:business_list`, nav link in topbar next
   to Pages/Leads): table — `company_name`, `city`, `cities` served,
   `move_type`, active status badge, `total_leads_received`,
   `priority_score`, `created_at`. Filter pills by active/inactive
   (mirror the existing status-pill filter pattern from the leads list).
   Search by name/email/city. Clickable row → detail, same pattern as
   `lead-table`.
2. **Business detail/edit** (`dashboard:business_detail`):
   - Core info form: `company_name`, `company_number`, `email`, `phone`,
     `website`, `address`, `postal_code`, `city`, `tiltaleform`,
     `first_name`, `last_name`.
   - Coverage: `cities` and `move_type` — free-text comma-separated
     strings today; rendered as a plain comma-separated text input for
     v1 (no tag-picker/FK redesign — that's a bigger schema change
     touching the matching query in `apps/core/views.py` too, out of
     scope here).
   - Lead settings: `leads_per_day`/`week`/`month`, `priority_score`, and
     an **active toggle** — the main gap this part closes: a one-click
     activate/deactivate control (POST + redirect, like `update_status`
     for leads) instead of requiring Django admin.
   - Public profile: logo upload/replace, `about_us`, `faq` — same fields
     the business edits in `edit_public_profile`, now editable by staff
     too.
   - Image gallery: view current `BusinessImage` set (respect the
     6-image cap), add/remove.
   - Reviews: list existing `Review` rows for this business with
     add/edit/delete forms (rating, name, comment) — the only place
     reviews are authored anywhere in the app.
   - Leads/jobs received: read-only list of `JobDistribution` rows where
     this business is `business_1`/`business_2`/`business_3` — will be
     empty today per the pipeline resolution above; the template carries
     a comment saying so.
   - "View public profile" link — reverses `public_business_profile` with
     `business.id`.
3. **Quick activate/deactivate** from the list view (POST-only action,
   `dashboard:business_toggle_active`) — WP-style inline status toggle,
   no detail page required for this one common action.
4. Norwegian UI copy matching existing dashboard vocabulary.

### Non-goals for Part 2

- No new city/move-type taxonomy model — keep the existing comma-separated
  string fields as-is.
- No public-facing review submission form.
- Don't change the actual matching algorithm in
  `apps/core/views.py send_flytteforesporsel` (`random.sample` ignoring
  `priority_score`, etc.) — Part 2 is an admin surface over existing data,
  not a rewrite of the matching engine.
- "Duplicate business" is skipped — a business isn't a content template to
  clone.

### Acceptance criteria

- Staff can list all businesses, filter by active/inactive, search, open
  one, edit every field above, toggle active status, manage its gallery
  images and reviews — entirely from the branded dashboard, no Django
  admin needed.
- All mutating actions are POST + CSRF, following the exact pattern
  already used in `apps/dashboard/views.py` (`update_status`,
  `delete_lead`).
- The "leads received" list is wired to `JobDistribution`, and the
  business-detail template carries a comment confirming whether that data
  is currently populated by live traffic (it is not, per the pipeline
  resolution above).
